# Security policy

## Reporting a vulnerability

**Do not open a public issue.** Use GitHub's private reporting:

1. Go to [Security → Report a vulnerability](https://github.com/jeloercc/pqc-sdk/security/advisories/new).
2. Describe the problem: affected version, impact, and steps or a PoC to
   reproduce it.

What to expect:

- **Acknowledgment within 72 hours.**
- Assessment and a fix plan (or a justified dismissal) within 14 days.
- Coordinated disclosure: we publish the advisory and credit the reporter
  (if you want it) together with the patched version.

## Supported versions

| Version      | Support                         |
| ------------ | ------------------------------- |
| Latest `0.x` | ✅ Security fixes               |
| Older        | ❌ Update to the latest version |

While the project is on `0.x`, security fixes land only on the latest
published version of `@pqc-sdk/core` and `@pqc-sdk/cli`.

## Scope

**In scope:** the code in this repo — the `@pqc-sdk/core` API (hybrid
encryption, signatures, key serialization), the CLI, and any incorrect use we
make of the primitives (nonces, derivation, handling of sensitive material).

**Out of scope (report upstream):** the primitives themselves. ML-KEM and
ML-DSA come from [`@noble/post-quantum`](https://github.com/paulmillr/noble-post-quantum)
and AES-256-GCM from [`@noble/ciphers`](https://github.com/paulmillr/noble-ciphers);
vulnerabilities in those implementations should be reported to their
maintainers.

**Not implemented (deliberate scope decision, not oversight):** SLH-DSA
(FIPS 205). Recorded with dates and reasoning in
[`docs/compliance/FIPS-205-MATRIX.md`](./docs/compliance/FIPS-205-MATRIX.md).
Three factors drove it, verified against FIPS 205 Table 2 rather than
estimated: signature size (7,856 bytes for SLH-DSA-128s up to 49,856 bytes
for SLH-DSA-256f, versus 3,309 bytes for ML-DSA-65 — 2.4×–15× larger); the
pure-JS performance cost of SPHINCS+'s tens-of-thousands-of-hash-invocations
signing/verification path, which has no native acceleration here or in
`@noble/post-quantum`; and use-case fit — SLH-DSA is a hedge against a
lattice cryptanalytic break, aimed at firmware signing and long-lived roots
of trust, not the request/response and file-level use this SDK targets.
**ML-DSA-65 is the recommended signature algorithm.** A consumer with a
genuine SLH-DSA requirement likely needs a CMVP-validated module rather than
a self-assessed JS library — see the threat model below for what
"self-assessed" means in this repo. Reopenable on a concrete use case.

## Threat model: known limits

So you can assess whether the SDK fits your case:

- `@noble/post-quantum` has no independent audit yet. Its most recent
  self-audit (Apr 2026) covered 0.6.1; we now pin 0.7.1, which post-dates
  that self-audit.
- As with any JavaScript implementation, there are no strict constant-time
  execution guarantees; local side-channel attacks are outside the threat
  model.
- **No memory zeroization.** Shared secrets (the AES-256 key), decrypted
  plaintext, and secret-key bytes are not wiped after use — this SDK contains
  no wiping code at all. `@noble` _does_ zeroize its own internal scratch
  buffers (46 `cleanBytes` call sites across the ML-KEM, ML-DSA and hybrid
  modules in `@noble/post-quantum` 0.7.1), but that never reaches the values it
  hands back: the shared secret, the plaintext and the key bytes we hold are
  ours, and nothing wipes them. For those, JavaScript offers no reliable
  zeroization primitive — a moving garbage collector may relocate a
  `Uint8Array` and leave copies that a later `fill(0)` cannot reach — so this
  is an ecosystem limitation, not something the SDK can fully close.
- The keys generated by `pqc init` are development keys and the CLI warns
  about it: do not use them in production.

## Randomness source

FIPS 203 §3.3 requires that the randomness consumed by ML-KEM.KeyGen and ML-KEM.Encaps
"shall be generated using an approved RBG, as prescribed in SP 800-90A, SP 800-90B, and
SP 800-90C", with a security strength of at least 192 bits for ML-KEM-768.

**That requirement lands on the deployment, not on this SDK, and we do not claim to
satisfy it.** What the SDK controls, it does: randomness is drawn fresh for every
invocation, sampled inside the module rather than accepted from callers on any production
path, and a failure of the platform generator now surfaces as a distinct `RBG_FAILURE`
error instead of being reported as an invalid key. What the SDK does not control is the
generator behind `crypto.getRandomValues`, which belongs to the host runtime:

| Runtime                          | Randomness API resolved at run time                                                      |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| Node 20+                         | `globalThis.crypto.getRandomValues` (Web Crypto, backed by OpenSSL's `RAND_bytes`)       |
| Deno                             | `globalThis.crypto.getRandomValues`                                                      |
| Cloudflare Workers               | `globalThis.crypto.getRandomValues` (workerd)                                            |
| React Native (Expo)              | `react-native-get-random-values`, which bridges to `SecRandomCopyBytes` / `SecureRandom` |
| Hermes standalone (example only) | **`Math.random`** — see below                                                            |

This table documents where the bytes come from. It makes **no claim about the SP 800-90
approval status of any of them**; establishing that is the responsibility of whoever
deploys the complete module, and it is exactly the delegation FIPS 203 makes on its own
cover page, point 13: "conformance to this standard does not ensure that a particular
implementation is secure… The responsible authority in each agency or department shall
ensure that an overall implementation provides an acceptable level of security."

⚠️ The `examples/hermes-standalone` shim fills bytes from `Math.random`, which is **not
cryptographically secure**. That example exists solely to validate that the Hermes engine
can execute the SDK; it is not a usable configuration. A real React Native app must
install `react-native-get-random-values` and import it before the SDK, as
`examples/react-native-expo` does.

If your deployment must demonstrate FIPS 203 §3.3 compliance, the RBG — not this
library — is what has to be validated. See `docs/compliance/FIPS-203-MATRIX.md` row
F203-12.

## Dependency policy

The cryptographic dependencies (`@noble/post-quantum`, `@noble/ciphers`) are
pinned to **exact versions** in `@pqc-sdk/core`, not caret ranges. A downstream
`npm install` therefore resolves the exact primitive build that shipped and
passed the NIST vectors; bumps are made deliberately behind the vector tests.
Published tarballs include source maps (`*.js.map` / `*.cjs.map`) — expected for
this MIT project, noted here so it is a conscious choice.
